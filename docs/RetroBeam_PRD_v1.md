## 0. Revision Notes (v1.1)

v1.0 was drafted before Epic 1 shipped. v1.1 reconciles it with the merged code (Phoenix 1.8.5, LiveView 1.1, Tailwind 4 + daisyUI 5) and with the current Anthropic API, and tightens the remaining backlog so each story can ship as one reviewable PR. Epic 1 is unchanged.

**Architecture**

- **Write-through persistence.** v1.0 had the session GenServer snapshot state to Postgres every 30 seconds, which loses up to 30 seconds of cards and votes on a crash or a Fly machine stop. Every mutation is now written to Postgres inside the GenServer call, then broadcast. The GenServer serializes writes and caches state; Postgres is the source of truth.
- **No singleton AI GenServer.** A single `AIAgent` process would serialize every retro's AI calls. Grouping requests now run in a `Task.Supervisor` child; report generation stays in Oban.
- **One PubSub topic per retro** (`retro:{id}`) plus Presence on `retro:{id}:presence`. LiveView subscribes to PubSub directly; no hand-written Channels.
- **Timer without per-second broadcasts.** The session process stores `ends_at` and broadcasts only state changes and expiry; each LiveView re-renders from `ends_at` on a local one-second tick.

**Anthropic integration (Epic 6)**

- `tool_use` with forced `tool_choice` is rejected by current models (Claude Opus 5.5, Claude Sonnet 5.5). Structured output now uses `output_config.format` with a JSON schema.
- Default model `claude-sonnet-4-20250514` replaced with `claude-opus-5-5`; `claude-sonnet-5-5` or `claude-haiku-5-5` can be set through `ANTHROPIC_MODEL` to cut cost. Requests send `anthropic-version: 2026-10-21` and no `temperature`.
- Req's built-in retry and Oban's retry replace the hand-rolled exponential backoff, so a failure is never retried twice over.
- Tests stub HTTP with `Req.Test` instead of Mox, so no new test dependency is needed.
- The report is stored as structured JSON and rendered with HEEx; the Markdown export is generated by the app. No Markdown library and no model-written HTML.
- AI features are off when `ANTHROPIC_API_KEY` is unset (it was "Required" in v1.0).
- E6-S3 (the client) is built first in Epic 6; E6-S1 and E6-S2 depend on it.

**Backlog fixes**

- Every story now lists **Depends on**. Section 8 gives the exact build order.
- E2-S4 was the largest story and held API for cards, groups and votes that later stories own. It now covers the process lifecycle, state loading and phase changes only; each later story adds its own mutations.
- Gaps filled: a minimal `/retros/:id` page in E2-S2 (v1.0 redirected to a page that no story built), the dashboard list of retros, participant-only access to a retro, Setup-phase options editing (E2-S5), the "hide cards during Collect" toggle (E3-S1), a "Finish retro" action that ends a retro (E2-S5), and the 0-vote edge case for discussion.
- Clarified rules: groups contain cards from one column; votes go to ungrouped cards or to groups, never to cards inside a group; join codes avoid look-alike characters and are case-insensitive.
- Removed impossible or misleading criteria: "optimistic update" (LiveView renders after the server replies), "removed within 2 seconds (Presence heartbeat)" (Presence removes a user when their LiveView process exits), duplicate AC numbering in E3-S1.
- Drag and drop uses a LiveView 1.1 colocated hook over native HTML5 drag events, with a keyboard alternative for WCAG. SortableJS is no longer required.
- daisyUI class names in acceptance criteria are now guidance, not requirements: `docs/DESIGN_SYSTEM.md` governs styling.

**Test plan**

- Wallaby is not a dependency and needs a browser driver in CI. Multiplayer scenarios are tested with two or more `Phoenix.LiveViewTest` sessions in one test; browser E2E is deferred (section 10).
- Coverage is measured with the built-in `mix test --cover`.

## 1. Executive Summary

RetroBeam is a focused demo application that showcases real-time multiplayer collaboration using Phoenix/Elixir and the BEAM VM. The application implements a single agile ceremony (the Sprint Retrospective) with full multiplayer presence, real-time voting, AI-suggested card grouping, per-topic discussion timers, and AI-powered post-retro action item reports via the Anthropic API.

This demo validates the architectural thesis from our research: Phoenix Channels, PubSub, and Presence provide multiplayer primitives out of the box that other stacks require multiple external services to replicate. By constraining scope to retrospectives only, we can deliver a polished, production-quality experience that demonstrates these capabilities without the complexity of a full work management platform.

### 1.1 Goals

- Demonstrate real-time multiplayer collaboration with LiveView, PubSub and Presence
- Showcase AI-native integration patterns using supervised tasks, Oban jobs and Anthropic Claude
- Validate the Pure LiveView approach for interactive board-style UIs
- Deploy to Fly.io as a publicly accessible demo with basic authentication
- Produce a codebase structured for AI coding agent development workflows

### 1.2 Non-Goals

- Full work management features (sprints, backlogs, epics, roadmaps)
- Offline support or local-first architecture
- ElectricSQL integration (deferred to Phase 2 per research roadmap)
- Rich text editing with CRDTs (cards are plain text for the demo)
- Enterprise features (SSO, SCIM, audit logs, RBAC beyond facilitator/participant)

## 2. Technology Stack

| Layer | Technology | Rationale |
|-------|-----------|-----------|
| **Runtime** | Elixir 1.19 / OTP 28 | BEAM VM process model maps directly to the session and connection model |
| **Web Framework** | Phoenix 1.8.5 / LiveView 1.1 | Built-in PubSub and Presence; LiveView diffs for real-time UI; colocated JS hooks |
| **Database** | PostgreSQL 16+ (CI runs 17) | Ecto integration, Oban job queue |
| **Background Jobs** | Oban 2.20 | Postgres-only, ACID-compliant job processing for AI report generation |
| **AI Integration** | Anthropic Messages API | Card grouping suggestions and the post-retro summary, both as structured JSON output |
| **HTTP Client** | Req 0.5 | Elixir-native HTTP client; `Req.Test` for stubbing in tests |
| **Authentication** | phx.gen.auth (magic links + optional password) | Phoenix 1.8 generator with magic-link registration and bcrypt password hashing |
| **Deployment** | Fly.io + Docker | Single machine for the demo; release migrations on deploy |
| **CSS / UI** | Tailwind CSS 4 + daisyUI 5 (vendored plugin) | Theme tokens in `assets/css/app.css`; see `docs/DESIGN_SYSTEM.md` |
| **Testing** | ExUnit, Phoenix.LiveViewTest, Oban.Testing, Req.Test | Unit, LiveView integration and multi-session tests without a browser |

### 2.1 Key Architecture Decisions

**Pure LiveView (no SPA):** For a board-style retro UI, LiveView provides real-time updates for free via server-pushed diffs. Drag-and-drop for card grouping uses a LiveView 1.1 colocated hook (`<script :type={Phoenix.LiveView.ColocatedHook}>`) over native HTML5 drag events, so no JS dependency is added. Every drag action also has a keyboard-operable alternative.

**Server-Authoritative State:** All retro state lives on the server. Clients receive diffs via LiveView and never hold authoritative state.

**GenServer Per Retro Session:** Each active retrospective runs as a `RetroServer` GenServer, registered in a `Registry` by retro id and started on demand under a `DynamicSupervisor`. It serializes all mutations for that retro, writes each one through to Postgres, then broadcasts it. This gives one ordering of events per retro, fault isolation (one retro crashing does not affect others), and fast in-memory reads. Because Postgres holds every change, a restarted process rebuilds its state with one query.

**Contexts take a scope:** Following Phoenix 1.8 conventions, public context functions take `%Retrobeam.Accounts.Scope{}` as their first argument and authorize against `scope.user`.

**AI calls off the hot path:** Grouping suggestions run in a `Task.Supervisor` child started by the session process; the report runs as an Oban job. Neither blocks a LiveView or the session process. Results are broadcast on the retro topic.

**Styling:** `docs/DESIGN_SYSTEM.md` is the source of truth. daisyUI components (`card`, `badge`, `btn`, `steps`, `countdown`, `skeleton`) are a good fit where they map cleanly, but stories do not require a specific component class. Themes are configured in `assets/css/app.css` (Tailwind 4 has no `tailwind.config.js`).

**Single node:** The `Registry` is node-local, so the demo runs one Fly machine. Running several machines would need a cluster-wide registry (see section 10).

## 3. Feature Breakdown by Module

The application is organized into six modules, each representing a cohesive area of functionality. Modules are designed to be developed and tested independently by an AI coding agent.

### 3.1 Module: Authentication & User Management

Handles user registration, login, and session management. Provides the identity layer that Presence and card authorship depend on.

- User registration with email (magic link, no password required at registration)
- Session-based authentication via phx_gen_auth (optional password via settings)
- User profile with display name and avatar color (auto-assigned)
- Protected routes requiring authentication

### 3.2 Module: Retro Session Lifecycle

Manages the creation, configuration, and phase progression of retrospective sessions. A retro moves through defined phases: Setup, Card Collection, Grouping, Voting, Discussion, and Summary.

- Create a new retro with a selected template (Start/Stop/Continue, Mad/Sad/Glad, 4Ls, Sailboat, custom)
- Generate a shareable join code or link
- Facilitator controls phase transitions
- GenServer process per active retro holding all session state
- Every mutation is written through to Postgres before it is broadcast, so a crashed or stopped process loses nothing
- Session processes stop on their own after 30 minutes with no connected participants

#### 3.2.1 Retro Phases

| Phase | Description | Facilitator Actions |
|-------|-------------|-------------------|
| **Setup** | Configure options and share the join code | Set vote limit, multi-vote, anonymous cards, hide cards during Collect |
| **Collect** | All participants submit cards to columns. Cards are hidden or visible per facilitator setting | Toggle card visibility, advance to Grouping |
| **Group** | AI suggests card groupings. Facilitator reviews, adjusts, and confirms groups | Accept/reject AI suggestions, manually drag cards between groups, label groups |
| **Vote** | Participants allocate a fixed number of votes across cards/groups | Set vote limit, advance to Discussion when voting closes |
| **Discuss** | Facilitator walks through cards/groups in vote-rank order with per-topic timer | Start/stop timer per topic, record notes, advance topics |
| **Summary** | AI generates action item report from discussion notes and card content | Trigger report generation, review and export report |

### 3.3 Module: Card Management

Handles creation, editing, and real-time synchronization of retrospective cards across all connected participants.

- Create cards assigned to a specific column (defined by template)
- Edit and delete own cards during the Collect phase
- Optional anonymous mode where card authors are hidden
- Real-time broadcast of card creation/edit/delete to all participants via PubSub
- Card grouping: drag a card onto another card in the same column to form a group, or into an existing group; a keyboard-operable "Move to group" control does the same without dragging
- Group labeling by facilitator
- All grouping operations broadcast in real-time; every participant sees the same board state

### 3.4 Module: Voting System

Implements real-time dot-voting on cards and groups. Vote tallies update live for all participants as votes are cast.

- Each participant receives a configurable number of votes (default: 5)
- Votes can be placed on individual cards or groups
- Multiple votes on the same item allowed (configurable)
- Real-time vote count updates broadcast to all participants via PubSub
- Remaining vote count displayed per participant
- Vote results determine discussion order (highest votes first)

### 3.5 Module: Discussion & Timer

Manages the facilitated discussion phase with per-topic timing, note-taking, and topic progression.

- Topics presented in descending vote order
- Per-topic countdown timer visible to all participants in real-time
- Configurable default timebox per topic (e.g., 5 minutes)
- Timer start/stop/reset controlled by facilitator
- Visual and optional audio alert when timebox expires
- Discussion notes field per topic (facilitator-editable, visible to all)
- Action item capture during discussion (assignee, description, due date)
- Elapsed time per topic recorded for the summary report

### 3.6 Module: AI Report Generation

Integrates with the Anthropic Messages API to provide two AI-powered capabilities: card grouping suggestions during the Group phase, and a structured post-retro summary report. Both are optional: when `ANTHROPIC_API_KEY` is not set, the AI controls are hidden and the retro works without them. Card text, notes and participant display names are sent to Anthropic; for anonymous retros, author names are never sent.

#### 3.6.1 Card Grouping Suggestions

- During the Group phase, the AI agent analyzes all card text and suggests logical groupings
- Suggestions appear as a facilitator-only overlay with Accept/Reject per suggestion
- The request runs in a supervised `Task` (not in the LiveView or session process) and the result is broadcast on the retro topic
- The request asks for JSON that matches a schema (Messages API structured outputs, `output_config.format`)
- Facilitator can re-trigger suggestions after manual adjustments

#### 3.6.2 Post-Retro Summary Report

- Triggered by facilitator at the end of the Summary phase
- Inputs: all cards, groups, vote counts, discussion notes, action items, timing data
- AI returns structured JSON: executive summary, key themes, action items with owners and dates; participation and timing metrics are computed by the app, not the model
- Report rendered by a HEEx template from the stored JSON and exportable as Markdown generated by the app (no model-written HTML is ever rendered)
- Generation runs as an Oban job to handle API latency without blocking the LiveView process
- Progress indicator shown to all participants during generation

## 4. Data Model

All schemas live under `Retrobeam.Retros` (for example `Retrobeam.Retros.RetroSession`) and use `utc_datetime` timestamps. Active retros are cached in their `RetroServer` process, but every change is written to these tables first.

| Schema | Key Fields | Relationships |
|--------|-----------|---------------|
| **User** | id, email, hashed_password, display_name, avatar_color | has_many :retro_participations |
| **RetroSession** | id, title, template (Ecto.Enum), phase (Ecto.Enum: setup, collect, group, vote, discuss, summary), join_code (unique), vote_limit (default 5), allow_multiple_votes (default true), anonymous (default false), hide_cards_during_collect (default false), topic_timebox_seconds (default 300), current_topic_id, facilitator_id, started_at, ended_at | belongs_to :facilitator (User), has_many :participations, :columns, :card_groups, :discussion_topics; has_one :report |
| **RetroColumn** | id, name, description, position, retro_session_id | belongs_to :retro_session, has_many :cards |
| **Card** | id, body, author_id, retro_column_id, card_group_id, position | belongs_to :author (User, kept even in anonymous mode so authors can edit their own cards), :column, :card_group (optional) |
| **CardGroup** | id, label, retro_column_id, retro_session_id, position | belongs_to :retro_session, :column; has_many :cards. A group holds cards from one column only. |
| **Vote** | id, user_id, retro_session_id, card_id, card_group_id | One row per vote. Exactly one of card_id or card_group_id is set (check constraint). |
| **RetroParticipation** | id, user_id, retro_session_id, role (Ecto.Enum: facilitator, participant), joined_at | unique index on (user_id, retro_session_id) |
| **DiscussionTopic** | id, retro_session_id, card_id, card_group_id, position, vote_count, notes, elapsed_seconds, discussed_at | Exactly one of card_id or card_group_id is set (check constraint) |
| **ActionItem** | id, description, assignee_id, discussion_topic_id, due_date, status (Ecto.Enum: open, done) | belongs_to :assignee (User, must be a participant), :discussion_topic |
| **RetroReport** | id, retro_session_id (unique), status (Ecto.Enum: pending, generating, complete, failed), content (map), content_markdown, error, model, input_tokens, output_tokens, generated_at | belongs_to :retro_session |

Notes:

- `join_code` is 6 characters from an alphabet without look-alikes (no 0/O, 1/I/L), stored uppercase, matched case-insensitively.
- A retro has ended when `ended_at` is set (by "Finish retro", E2-S5). Ended retros are read-only.
- Each schema story adds only the tables it needs; migrations are not front-loaded.

## 5. Real-Time Architecture

### 5.1 PubSub Topics

Each participant has one LiveView process on one WebSocket. LiveViews subscribe to Phoenix PubSub topics directly; the app defines no custom Channels.

| Topic | Purpose | Example events |
|-------|---------|----------------|
| `retro:{retro_id}` | Everything that changes the board, broadcast by `RetroServer` after the write commits | `{:phase_changed, phase}`, `{:card_created, card}`, `{:card_updated, card}`, `{:card_deleted, card_id}`, `{:group_changed, group}`, `{:vote_totals, totals}`, `{:timer, timer_state}`, `{:topic_changed, topic}`, `{:report_status, status}` |
| `retro:{retro_id}:presence` | Phoenix.Presence for connected participants | `presence_diff` |
| `retro:{retro_id}:facilitator` | Facilitator-only events | `{:grouping_suggestions, suggestions}` |

Broadcast payloads are plain tagged tuples defined in one module (`Retrobeam.Retros.Events`) so the LiveView and the server agree on shapes.

### 5.2 Presence Tracking

`RetrobeamWeb.Presence` (a `Phoenix.Presence` module, added to the supervision tree) tracks each connected LiveView under the user id with metadata: display name, avatar color and role. A participant appears when their LiveView mounts with a connected socket and disappears when that process exits (tab closed, navigation, or the socket timing out).

### 5.3 Session Process

Each active retro runs one `RetroServer`, registered in `Retrobeam.Retros.Registry` and started on demand under `Retrobeam.Retros.SessionSupervisor` (`restart: :transient`). Every state change follows the same path:

1. LiveView receives a user event and calls the context function with the current scope
2. The context calls the retro's `RetroServer` (starting it if needed)
3. The server checks the phase and the caller's role, then writes to Postgres
4. On success it updates its cached state and broadcasts on `retro:{id}`
5. Every subscribed LiveView applies the event and pushes a diff to its client

The server monitors connected LiveView processes and stops itself 30 minutes after the last one leaves.

## 6. Test Plan (80% Coverage Target)

Unit tests cover business rules and the session process; LiveView tests cover interactions and broadcasts, including multiplayer scenarios with several live sessions in one test. Coverage is measured with `mix test --cover`.

### 6.1 Unit Tests

| Module | Test Focus | Key Scenarios |
|--------|-----------|---------------|
| Templates | Template definitions, column generation | Each template produces correct columns; custom template validation |
| Retros context | Creation, joining, authorization | Join code generation and uniqueness, duplicate joins, non-participant access |
| RetroServer | Lifecycle, phase rules, write-through | Start on demand, state rebuilt from Postgres after a crash, valid and invalid phase changes, facilitator-only actions, idle shutdown |
| Card Management | CRUD, visibility, grouping | Card in the correct column, edit and delete own card only, group create/merge/dissolve, same-column rule |
| Voting | Allocation, limits, tallying | Vote limit, multi-vote off, removal, totals, 0 and max votes |
| Discussion & Timer | Ordering, timer state | Rank order and tie-breaks, start/pause/reset/next, expiry, elapsed time recorded |
| Anthropic client | Request building, response handling | Headers and body, structured output parsing, refusals, `max_tokens` stop, HTTP errors, missing API key |

### 6.2 Integration Tests

| Test Area | Approach | Key Scenarios |
|-----------|----------|---------------|
| Card board | Phoenix.LiveViewTest | Cards appear, change and disappear for every connected session; phase changes update the UI |
| Real-time voting | Two LiveView sessions | A vote by user A updates the total for user B; remaining votes shown per user |
| Presence | Several LiveView sessions | Join appears for others; leave removes the user; facilitator badge |
| Phase controls | LiveViewTest + process assertions | Facilitator advances; participant cannot; state is in Postgres after each change |
| Timer | PubSub subscription in test | Start/pause/expiry events reach every session |
| AI integration | `Req.Test` stubs | Suggestions render for the facilitator only; report progress and completion; API errors shown, not crashed |
| Oban jobs | `Oban.Testing` (inline in test) | Report job enqueued and completed; failure marks the report failed |

### 6.3 End-to-End Tests

Browser E2E (Wallaby or Playwright) is deferred; see section 10. The flows it would cover (two-player retro, facilitator-only controls, live vote sync, drag-to-group, reconnect) are each covered by a multi-session LiveView test in the matching story.

### Epic 2: Retro Session Lifecycle

Core session management: templates, creation, joining, the session process and phase control.

#### E2-S1: Retro Template Definitions

**As a facilitator**, I need predefined retro templates so that I can quickly start a retro without manual column setup.

**Depends on:** none

**Acceptance Criteria:**

1. `Retrobeam.Retros.Template` defines templates as plain data (no database table): Start/Stop/Continue (3 columns), Mad/Sad/Glad (3 columns), 4Ls (Liked/Learned/Lacked/Longed For, 4 columns), Sailboat (Wind/Anchor/Rocks/Island, 4 columns), and Custom
2. `Template.all/0` lists the named templates with key, name, description and columns, in display order
3. `Template.columns/1` returns a list of `%{name, description, position}` maps for a named template, positions starting at 0
4. `Template.columns(:custom, names)` accepts 2 to 6 column names; names are trimmed, must be non-blank, at most 40 characters, and unique ignoring case; it returns `{:ok, columns}` or `{:error, reason}`
5. `Template.keys/0` returns the template keys, for use as the `Ecto.Enum` values on `RetroSession.template`
6. Tests: each named template returns the correct column count, names and positions; custom validation (too few, too many, blank, too long, duplicate, whitespace trimming); unknown template keys are rejected

#### E2-S2: Create Retro Session

**As a facilitator**, I need to create a new retrospective by selecting a template so that my team can participate.

**Depends on:** E2-S1

**Acceptance Criteria:**

1. Migrations and schemas for `RetroSession`, `RetroColumn` and `RetroParticipation` (section 4)

4. LiveView at `/retros/new` shows a title field and one choice per template with a preview of its columns; choosing Custom reveals 2 to 6 column name inputs, validated live
5. On success the facilitator is redirected to `/retros/:id`
6. A minimal `RetroLive.Show` at `/retros/:id` shows the title, the join code with a copyable join link, the current phase and the columns. Only participants can open it; anyone else is redirected to `/retros/join/:code` with a flash
7. The `/retros` dashboard lists the user's retros (facilitated and joined), newest first, with phase, and has a "New retro" button
8. `/retros/new`, `/retros/join` and `/retros/join/:code` are declared before `/retros/:id` in the `:authenticated` live session
9. Tests: creation with each template, custom columns, join code format and collision retry, records created in one transaction, non-participant redirect, dashboard listing

#### E2-S3: Join Retro Session

**As a participant**, I need to join an existing retro with a join code or link so that I can take part.

**Depends on:** E2-S2

**Acceptance Criteria:**

1. LiveView at `/retros/join` shows a form for a 6-character join code; `/retros/join/:code` pre-fills it
2. Codes are matched case-insensitively, ignoring surrounding spaces
3. A valid code creates a `RetroParticipation` with `role: :participant` and redirects to `/retros/:id`

7. Unauthenticated visitors to `/retros/join/:code` are sent to log in and return to the join page afterwards
8. Tests: valid join, lower-case code, invalid code, duplicate join, ended retro, return-to after login

#### E2-S4: Retro Session Process

**As the system**, I need one process per active retro that serializes its changes so that every participant sees the same events in the same order.

**Depends on:** E2-S2

**Acceptance Criteria:**

1. `Retrobeam.Retros.RetroServer` is a GenServer registered in `Retrobeam.Retros.Registry` by retro id and started on demand under the `Retrobeam.Retros.SessionSupervisor` DynamicSupervisor with `restart: :transient`
2. `RetroServer.ensure_started/1` starts the process if needed and is safe to call concurrently
3. On start the server loads the session, columns and participants from Postgres
4. `get_state/1` returns the cached state; `join/2` registers the calling LiveView (monitored) and returns the state
5. `RetroLive.Show` calls `join/2` and subscribes to `retro:{id}` when its socket is connected
6. The server stops itself after 30 minutes with no joined LiveViews (configurable, set short in tests); a later visit starts a fresh process from Postgres
7. Mutations are added by later stories using the same pattern: authorize, write to Postgres, update state, broadcast `Retrobeam.Retros.Events`
8. Tests: start on demand, concurrent `ensure_started`, state loaded from Postgres, state rebuilt after the process is killed, idle shutdown after the last LiveView leaves

#### E2-S5: Phase Transitions and Setup Options

**As a facilitator**, I need to control the retro's phases and options so that the retrospective follows a structured flow.

**Depends on:** E2-S4

**Acceptance Criteria:**

1. The retro page shows a phase indicator for Setup, Collect, Group, Vote, Discuss and Summary with completed, current and upcoming states (text labels plus `aria-current`, not color alone)
2. Only the facilitator sees a "Next phase" button; `RetroServer.advance_phase/2` rejects anyone else with `{:error, :unauthorized}`
3. Phases move forward one step at a time: Setup, Collect, Group, Vote, Discuss, Summary; no skipping and no going back
4. The new phase is written to Postgres, then broadcast as `{:phase_changed, phase}`; every connected participant's page updates without a refresh
5. During Setup the facilitator can edit options: vote limit (1 to 20), allow multiple votes per item, anonymous cards, and hide cards during Collect. Options lock once Setup ends
6. In Summary the facilitator sees "Finish retro", which sets `ended_at` and makes the retro read-only for everyone
7. Tests: every valid transition, skipping and going back rejected, participant rejected, broadcast received by a second LiveView session, phase and options persisted, Finish retro

### Epic 5: Discussion & Timer

#### E5-S1: Per-Topic Discussion Timer

**As a facilitator**, I need a timer for each topic so that the team manages its time and the report records how long each topic took.

**Depends on:** E4-S2

**Acceptance Criteria:**

1. The discussion view shows the current topic with a large countdown (mm:ss, announced to screen readers only on start, pause and expiry)
2. The facilitator sets the timebox (1 to 15 minutes, default 5) before or between topics
3. The facilitator can Start, Pause, Reset (back to the timebox) and Next topic
4. Timer state (running, `ends_at`, remaining when paused) lives in `RetroServer`; it broadcasts `{:timer, state}` on each change and schedules its own expiry message
5. Each LiveView re-renders the remaining time from `ends_at` on a local one-second tick, so all participants agree to within a second without per-second broadcasts
6. At 0 the countdown shows an expired state (with `motion-safe` pulse) for everyone; the timer does not go negative
7. Next topic records the topic's elapsed seconds (time actually run, excluding pauses) and `discussed_at`, then moves to the next topic with a fresh timer
8. Tests: start, pause, reset, next, expiry message, elapsed time excluding pauses, timebox validation, facilitator-only controls, broadcast to a second session

### Epic 6: AI Integration

AI features are optional. With no `ANTHROPIC_API_KEY`, AI controls are hidden and nothing calls the API. Build E6-S3 first.

#### E6-S1: AI Card Grouping Suggestions

**As a facilitator**, I need AI-suggested card groupings during the Group phase so that similar cards are found without reading every card.

**Depends on:** E6-S3, E3-S2

**Acceptance Criteria:**

1. In the Group phase the facilitator sees "Suggest groups"; pressing it (or "Re-analyze" later) asks the server to start one suggestion request for the retro; a request already in flight is not duplicated
2. The request runs under `Retrobeam.TaskSupervisor` and sends ungrouped and grouped card ids, bodies and column names (never author names) with a JSON schema for suggestions: label, column id and card ids
3. The response is validated: unknown card ids, cross-column suggestions and single-card groups are dropped
4. Suggestions are broadcast on `retro:{id}:facilitator`; only the facilitator's page shows the "AI suggestions" panel with each label and card previews
5. Accept applies a suggestion through the normal grouping calls (E3-S2); Reject dismisses it; Accept all applies every remaining suggestion
6. Failures (timeout, HTTP error, refusal, invalid output) show a dismissible error in the panel; the board keeps working
7. Tests (with `Req.Test`): request body, parsing and validation, panel shown only to the facilitator, accept/reject/accept all, duplicate request prevention, error display

#### E6-S2: Post-Retro Summary Report

**As a facilitator**, I need an AI-generated summary after the retrospective so that the team has a structured record of outcomes.

**Depends on:** E6-S3, E5-S2

**Acceptance Criteria:**

1. Migration and schema for `RetroReport`
2. In Summary the facilitator sees "Generate report"; pressing it creates or resets the retro's report as `pending` and enqueues `Retrobeam.Workers.RetroReportWorker` on the `ai_reports` queue (Oban `unique` per retro, `max_attempts: 3`)
3. The worker gathers the template, columns, cards (author names only if the retro is not anonymous), groups, vote counts, topics with notes and elapsed time, action items and participant names
4. The model returns JSON matching a schema: executive summary, key themes, recommended action items (description, owner, due date, priority); participation and timing metrics are computed by the app
5. The worker stores the JSON, a Markdown rendering generated by the app, the model id and token usage, and sets `complete`; on final failure it sets `failed` with a short error
6. Status changes are broadcast; every participant sees a loading state while the report is generating and a link when it is complete
7. `/retros/:id/report` renders the report with HEEx for participants only; a "Copy Markdown" button (colocated hook) copies the Markdown
8. The facilitator can regenerate a failed or complete report
9. Tests (with `Req.Test` and `Oban.Testing`): enqueue, payload assembly (anonymous and named), stored report, Markdown rendering, broadcasts, failure handling, report page access

#### E6-S3: Anthropic Client

**As the system**, I need a small Anthropic Messages API client so that AI features are configurable, testable and safe to fail.

**Depends on:** none (build first in Epic 6)

**Acceptance Criteria:**

1. `Retrobeam.AI.Anthropic` builds requests with Req: `POST /v1/messages`, headers `x-api-key` and `anthropic-version: 2026-10-21`, configurable base URL, model and receive timeout
2. Config comes from `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` (default `claude-opus-5-5`) in `config/runtime.exs`; `Retrobeam.AI.enabled?/0` is false when there is no key
3. `structured/2` takes a system prompt, user content, JSON schema and options (`max_tokens`, `effort`), sends `output_config: %{format: %{type: "json_schema", schema: schema}}`, and returns `{:ok, %{data: map, usage: usage, model: model}}`
4. Requests do not send `temperature`, `top_p` or `top_k` (rejected on API version 2026-10-21)
5. Errors are tagged tuples, never raises: `:not_configured`, `{:http_error, status, body}`, `:timeout`, `{:refusal, details}`, `:max_tokens`, `{:invalid_output, reason}`
6. Transient failures (429, 5xx, connection errors) use Req's built-in retry with at most 2 retries; Oban jobs set `retry: false` and rely on Oban's retries instead
7. In test, `config :retrobeam, Retrobeam.AI.Anthropic, plug: {Req.Test, Retrobeam.AI.Anthropic}` routes all calls to stubs
8. Tests: headers and body shape, success parsing, each error case, missing key

## 9. Deployment & Operations

### 9.1 Fly.io Configuration

- Single Fly machine with 1GB RAM (sufficient for demo scale: ~50 concurrent users); the session registry is node-local, so do not scale out without a cluster-wide registry
- Fly Postgres single-node for the demo (no HA needed)
- Fly secrets: `SECRET_KEY_BASE`, `DATABASE_URL`, and optionally `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`
- `auto_stop_machines = "stop"` with `min_machines_running = 1`; because every change is in Postgres, a stopped machine loses no retro data, only running timers
- Health check at `/healthz` (returns 200 when Ecto repo is connected)

### 9.2 Environment Configuration

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `DATABASE_URL` | Yes | N/A | PostgreSQL connection string |
| `SECRET_KEY_BASE` | Yes | N/A | Phoenix secret for signing cookies and tokens |
| `ANTHROPIC_API_KEY` | No | N/A | Enables AI features when set |
| `ANTHROPIC_MODEL` | No | claude-opus-5-5 | Model for AI features; `claude-sonnet-5-5` or `claude-haiku-5-5` cost less |

## 10. Future Considerations

These items are explicitly out of scope for the demo but inform architectural decisions to avoid painting ourselves into a corner.

- ElectricSQL read-path sync for instant UI responsiveness (Phase 2 per research roadmap)
- Live AI copilot streaming during discussion phase (real-time suggestions as teams talk)
- Rich text card bodies with Yjs CRDTs via y_ex

- Multi-node clustering for horizontal scaling: a cluster-wide session registry (`:global`, Horde, or `:pg`-based) on top of the existing DNSCluster setup
- Browser end-to-end tests (Wallaby or Playwright) for the two-player flow, drag-to-group and reconnect
- Facilitator view of per-person vote distribution; hiding vote totals until voting closes
- Export to PDF or integration with Jira/Linear/GitHub Issues for action item tracking
- Mobile-responsive or native mobile experience
- Persistent retro analytics dashboard across multiple retros
